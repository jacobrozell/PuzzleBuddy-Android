**Written:** 2026-10-28
**For:** an implementing agent who has not seen either codebase before. Follow it top to bottom.

**iOS repo (canonical behavior):** `jacobrozell/PuzzleBuddy`

## 0. How to use this plan

1. Read sections 1–3 fully before writing any code. They hold the decisions and the rules.
2. Do the work packages (WP) **in order**. Later packages assume earlier ones are done. Each WP lists:
   - **iOS source** — the Swift files to read. They are the spec. When this plan and the Swift code disagree, the Swift code wins. Write the disagreement down in `PARITY.md` → "Session log".
   - **Android files** — what to create or change.
   - **Steps** — numbered. Do them in order.
   - **Rules** — behavior that is easy to get wrong. Each one matches a bug iOS already fixed.
   - **Tests** — JVM unit tests to add (`app/src/test/...`).
   - **Done when** — check every box before moving on.
3. After each WP: run `./gradlew testDebugUnitTest`, fix failures, then commit (one commit per WP; see 2.6).
4. Do not skip the "Done when" boxes. Do not start Phase 4 UI work while Phase 3 tests are red.
5. If something is ambiguous and the iOS code does not settle it, pick the behavior that keeps user data safe, write it in the commit message, and move on.

## 2. Ground rules

### 2.1 Repo conventions (Android)

- Read `AGENTS.md`, `PARITY.md`, `STATUS.md`, `docs/telemetry.md` first.
- Package root: `app/src/main/kotlin/com/jacobrozell/puzzlebuddy/`. Below, paths are relative to that root unless they start with `app/`.
- Layers: `domain/` (pure Kotlin) → `data/` (Room, DataStore, repositories) → `ui/` (Compose + Hilt ViewModels). `support/` holds logging, Firebase, image helpers.
- Logging: **only** through `AppLogger` (`support/logging/AppLogger.kt`) with `info/warning/error` extensions. Never call Firebase directly.
- Hilt for DI. `@Singleton` repositories. ViewModels use `@HiltViewModel`.
- Match the style of the surrounding Kotlin: data classes, `object` for semantics helpers, `companion object` for factories, no comments that restate the code.

### 2.2 Porting rules (Swift → Kotlin)

| Swift | Kotlin |
|-------|--------|
| `enum X: String` with `rawValue` | `enum class X(val raw: String)` + `companion object { fun fromRaw(raw: String): X = entries.firstOrNull { it.raw == raw } ?: DEFAULT }` (same pattern as `PuzzleStatus`). |
| `class Puzzle: ObservableObject` (mutable) | Keep the immutable `data class Puzzle` and use `copy(...)`. Functions that mutate a puzzle on iOS (`clearLoan(on:)`, `pause(_:now:)`, `noteStatusChanged`) become functions that **return a new `Puzzle`**. |
| `UUID` | `String` (the Android model already uses `UUID.randomUUID().toString()`). |
| `Date` | `java.time.Instant`. Stored in Room as `Long` epoch millis. |
| `Calendar.current.startOfDay` | `instant.atZone(zoneId).toLocalDate()`. Pass `zoneId: ZoneId` and `clock: Clock` as parameters with defaults. |
| `TimeInterval` (seconds, Double) | `Long` seconds or `java.time.Duration`. |
| `UserDefaults` | `AnalyticsKeyValueStore` (already exists, SharedPreferences-backed) for small flags, or `AppPreferencesStore` (DataStore) for UI prefs. Use the **same key strings** as iOS (e.g. `PuzzleBuddy.WhatsNewSeenVersion`). |
| `throws` + `PuzzleStoreError` | `sealed class PuzzleStoreException(message) : Exception(message)` with the same cases and the same user-facing messages. |
| `modelContext.rollback()` | Do multi-row writes inside one Room transaction (`TransactionRunner`, WP3.1). An exception inside the block rolls it back. |

**Raw strings must match iOS exactly.** They end up in JSON backups and CSV and must round-trip across platforms:
- Status: `"Wishlist"`, `"To-Do"`, `"In-Progress"`, `"Completed"`, `"Abandoned"`.
- Every metadata enum uses `"None"` for "not set", then capitalized words (`"Landscape"`, `"Cardboard"`, `"Kept"`, `"Rectangular"`, `"Ribbon"`…). Copy them from `App/Helpers/PuzzleMetadataEnums.swift`.
- User-facing copy (titles, dialog text, empty states, accessibility labels): copy word-for-word from Swift unless it names an Apple-only thing (App Store, VoiceOver, iPhone, iPad, Duo). Replace those with Play Store, TalkBack, phone, tablet. Drop Duo.

### 2.3 Telemetry rules

- Event names and metadata keys are already allowlisted on Android (`support/logging/FirebaseAnalyticsEventMapping.kt`, `AnalyticsMetadataKeys.kt`). **Do not add or rename Analytics events.** If you think you need a new one, stop and add it to "Open questions" in `PARITY.md` instead.
- Log-only events (not allowlisted, e.g. `friend_created`, `puzzle_marked_on_loan`, `puzzle_marked_returned`, `store_review_requested`) are fine. They go to breadcrumbs only.
- **No PII** in metadata: never puzzle names, borrower names, notes, tags, barcodes, or raw seconds.
- After any change under `support/logging/`, run the parity check (2.5).

### 2.4 Tests

- Unit tests are JVM-only (`app/src/test/kotlin/...`, JUnit 4, `kotlinx-coroutines-test`). There is no Robolectric. **Do not add it.**
- Domain helpers: test directly.
- Repository: test with in-memory fakes of the DAOs plus a `TransactionRunner` that just runs the block (WP3.1, WP3.9).
- When an iOS test exists for the logic you port (`AppTests/*.swift`), port its cases. The tests are listed per WP.
- Use a fixed `Clock` in every test that touches time. Never call `Instant.now()` in a test.

```bash
cp app/google-services.json.example app/google-services.json   # once; gitignored

If your environment has no Android SDK or emulator, say so in the commit message and in your final report. Do not claim UI verification you did not do. Unit tests still need a JDK 17+ and the Android SDK for `testDebugUnitTest`. If the SDK is missing, push and let CI (`.github/workflows/ci.yml`) run it.

### 2.6 Commits

- One commit per WP (a big WP may take 2–3). Message: one sentence, imperative, ending with a period, like the existing history (`Add PuzzleAnalyticsMetadata and expand Analytics allowlist for iOS parity.`).
- Never commit `app/google-services.json`.
- Push to the work branch with `git push -u origin <branch>`. Do not open a PR unless asked.

### WP1.1 Five statuses + progress semantics

**iOS source:** `Helpers/PuzzleObject.swift` (`Status`, `accessibilityDescription`, `noteStatusChanged`), `Helpers/PuzzleProgressSemantics.swift`, `Helpers/PuzzleDateSemantics.swift`.

**Android files:** `domain/model/Puzzle.kt`, `domain/catalog/PuzzleProgressSemantics.kt`, `domain/catalog/PuzzleDateSemantics.kt` (new).

**Steps:**
1. `PuzzleStatus` gets 5 entries in this order: `WISHLIST("Wishlist")`, `TODO("To-Do")`, `IN_PROGRESS("In-Progress")`, `COMPLETED("Completed")`, `ABANDONED("Abandoned")`. Keep `fromRaw` defaulting to `TODO`.
2. Add `val accessibilityDescription: String` per status (copy the iOS strings, e.g. `"Wishlist, not yet owned"`).
3. `PuzzleProgressSemantics.progressFor`: `WISHLIST`, `TODO`, `ABANDONED` → 0; `COMPLETED` → 100; `IN_PROGRESS` → keep clamped value, but 0 or 100 become 10. (Rename to match iOS if you like; keep the old name working until all callers move.)
4. Add `fun Puzzle.withStatusChange(previous: PuzzleStatus, new: PuzzleStatus, now: Instant): Puzzle` that ports `noteStatusChanged`:
   - progress = `progressFor(new, current)`.
   - `IN_PROGRESS` and `startDate == null` → `startDate = now`.
   - `COMPLETED`, `startDate == null`, previous was `IN_PROGRESS` → `startDate = completionDate`.
   - `ABANDONED`, previous was `IN_PROGRESS`, `startDate == null` → `startDate = completionDate`.
5. Port `PuzzleDateSemantics` in full (`detailDateLabel`, `formDateSectionTitle`, `listTrailingDate`, `statusPillLabel`, `showsStartDatePicker`, `resolveStartDate`, `progressDaysLabel`, `dayCount`, `completionDayCounts`). `dayCount` counts calendar days between local dates, never negative.

**Tests:** port `AppTests/PuzzleDateSemanticsTests.swift`, the progress cases in `AppTests/PuzzleExpandedFeatureTests.swift`. Add: each status → expected progress; `withStatusChange` start-date rules.

**Done when:** [ ] 5 statuses with exact raw strings. [ ] tests green. [ ] existing callers compile (`when` branches on `PuzzleStatus` now need `WISHLIST`/`ABANDONED` — handle them everywhere the compiler complains).

### WP3.4 Timer commands

**iOS source:** `PuzzleStore.startTimer`, `pauseTimer`, `resetTimer`, `foldTimer`, `pauseSkewedTimers`, `commitTimerChange`, `logTimerPaused`.

**Steps:** (all take `now: Instant = Instant.now(clock)` and run in one transaction)
1. `startTimer(id)`: load row → `RecordNotFound`. Return early unless status is `IN_PROGRESS` and not already running. Fold every **other** puzzle with a non-null `timerRunningSince`, fold this one (drops a skewed open segment), set `timerRunningSince = now`. After commit: for each other puzzle log `puzzle_timer_paused` (`reason=other_started`, `duration_bucket` of its new accumulated seconds); then log `puzzle_timer_started`.
2. `pauseTimer(id)`: no-op if not running. Fold. Log `puzzle_timer_paused` (`reason=pause`).
3. `resetTimer(id)`: `total = elapsedSeconds(...)`. No-op if `total == 0` and not running. Zero both fields. Log `puzzle_timer_paused` (`reason=reset`, bucket of `total`). Logged hours/minutes are **not** touched.
4. "Fold" = `timerAccumulatedSeconds = elapsedSeconds(acc, runningSince, now)`; `timerRunningSince = null`.

**Rules:**
- Only one timer runs at a time.
- Background, lock, and process death do **not** pause the timer. Elapsed time is wall-clock from the stored anchor. Do not add lifecycle observers that pause.
- No per-second database writes. The UI ticks (WP5.3).

### WP3.5 Completion history: delete, update, reconcile, undo

**iOS source:** `PuzzleStore.deleteCompletion`, `updateCompletion`, `reconcileCompletions`, `undoLastCompletion`, `activeCompletionUndo`, `expireCompletionUndoIfNeeded`, `dismissCompletionUndo`; `docs/implementation/1.1.0-completion-history.md`; review fixes #3, #4, #8, #33, #36 in `ongoing/1.1.0-review-fixes.md`.

**Steps:**
1. `deleteCompletion(puzzleId, completionId, statusIfRemovingLast: PuzzleStatus? = null, logDeletedEvent: Boolean = true)`:
   - `RecordNotFound` if the puzzle is gone. `CompletionNotFound` if the completion is gone.
   - If it is the only completion **and** the puzzle is `COMPLETED` **and** `statusIfRemovingLast == null` → throw `StatusRequiredAfterRemovingLastCompletion` (before deleting anything).
   - In one transaction: delete the row, then `reconcile(puzzleId, statusIfRemovingLast)`.
   - After commit: clear the undo snapshot if its `completionId` matches. If `logDeletedEvent` → log `puzzle_completion_deleted` with `completion_number` = the removed row's number before renumbering.
2. `updateCompletion(puzzleId, completion)`: `CompletionNotFound` if missing. In one transaction: write `completedAt`, `startedAt`, time, rating; renumber all rows for that puzzle (`PuzzleCompletionSemantics.renumbered`); `reconcile(puzzleId, null)`. After commit: clear the matching undo snapshot; log `puzzle_completion_updated` with `completion_number`.
3. `reconcile(puzzleId, statusIfEmpty)` (inside a transaction):
   - Load completions. **If the load throws, throw `CompletionHistoryUnavailable`. Never treat a failed read as an empty list** (iOS fix #8).
   - Renumber 1…N and write the numbers back.
   - `timesCompleted = count`.
   - If count is 0 and status is `COMPLETED`: require `statusIfEmpty` (else throw `StatusRequiredAfterRemovingLastCompletion`). Set status. If `TODO` → progress 0. If `IN_PROGRESS` and progress ≥ 100 → progress 0 (iOS fix #4: never leave 100% on an In-Progress puzzle).
   - If count > 0: `completionDate` = newest `completedAt`.
4. `undoLastCompletion(puzzleId, now)`:
   - Snapshot must exist and match `puzzleId` → else `CompletionUndoUnavailable`. If expired (>5 min) → clear it and throw `CompletionUndoUnavailable`.
   - Remember the completion's number. `deleteCompletion(puzzleId, snapshot.completionId, statusIfRemovingLast = snapshot.previousStatus, logDeletedEvent = false)`.
   - Then set status = `snapshot.previousStatus`, progress = `snapshot.previousProgressPercent` and save (iOS fix #36: after a replay, undo restores the status the user had before tapping Complete, e.g. In-Progress, even though older completions remain).
   - Clear the snapshot. Log `puzzle_completion_undone` with `completion_number`.
   - Undo does **not** touch the timer or any prefilled logged time.
5. `activeCompletionUndo(puzzleId, now)`, `expireCompletionUndoIfNeeded(puzzleId, now)`, `dismissCompletionUndo(puzzleId)`: port as-is. The snapshot lives only in memory (it is "same session" by design).

**Tests:** port the completion cases from `AppTests/PuzzleReviewFixTests.swift`, `PuzzleExpandedFeatureTests.swift`, `PuzzleBuddyTests.swift` on the target branch. Must include:
- delete middle of 3 → numbers become 1,2; `timesCompleted == 2`.
- delete newest of N → `completionDate` = remaining newest.
- delete only completion without a status → throws, nothing deleted.
- delete only completion → `IN_PROGRESS` with progress 100 → progress 0. → `TODO` → progress 0.
- edit a date to before an older finish → numbers reorder.
- simulated completion-read failure → `timesCompleted` unchanged, exception thrown.
- undo within 5 min restores previous status/progress; after 5 min throws and clears.
- undo after a replay (puzzle completed twice) restores In-Progress, keeps completion #1.
- failed save during "mark complete" → no undo snapshot published.

**Done when:** [ ] all listed tests pass.
